## 1. Why the shape changes

A day of a client's logging is three rows in three tables — `wellness_logs`, `nutrition_logs`, and `training_logs` (migration 056) — each carrying `client_id` and `date` of its own, plus a fourth row above them, `daily_logs`, whose only fact is a `notes` column and whose id the three point at. Every reader that wants a day filters by client and date; none needs the parent. What the parent costs, all verified on DEV on 2026-09-25:

- **Two statements where one would do.** Each per-card save (`PATCH /api/client/daily-logs/[date]/wellness` and `…/nutrition`, `services/daily-log-card-service.ts`) first upserts the spine row to learn its id, then upserts its own row on `onConflict: "daily_log_id"`. The file's own header calls a spine row without a child "benign" and a half-written day something "the day rule keys on the client's check-in weeks" to survive — a shape that needs a paragraph to explain why it is safe is the shape CONVENTIONS §8 asks a plan to justify. DEV carries 14 childless, note-less spine rows (10 May – 10 Sep) from exactly that seam.
- **The key readers use is not the key the constraint enforces.** Each child is `UNIQUE (daily_log_id)`; uniqueness per `(client_id, date)` — what every reader, the seeds and the feed's chunking assume — holds only transitively through the spine's own `UNIQUE (client_id, date)`. CONVENTIONS §2 item 9 wants an upsert's conflict target backed by a real UNIQUE on the columns the write is keyed by.
- **The view hides absence.** `daily_logs_full` LEFT JOINs the three children onto the spine, so a reader cannot tell a wellness row with no scores from no wellness row — `services/daily-context-service.ts:86` and `lib/logged-days.ts:67` both say so, and every logged-day reader carries a "carries a reading" predicate to compensate. Counting spine rows once read a client who only trained as silent (the measurement-log workstream's D11, commit 5): the definition was fixed by derivation, the shape that invited it stayed.
- **Dead weight the spine keeps alive.** `training_logs` has had no writer since the Daily Pulse retired: DEV holds 726 rows on 2 clients, the newest dated 13 Aug, all written by the scale seed; its `trained` column is read by nothing but two row mappers that copy it onto a wire nobody reads (the `utils/daily-logs-aggregation.ts:72` reader commit 12's bullet names no longer exists — that file reads no `trained`); its `training_data` JSONB is read by nothing (ARCHITECTURE "JSONB Conventions" says so). The two `upsert_daily_log_atomic` overloads are in both catalogs with zero callers and bodies that name food-log columns migration 173 dropped (TECHNICAL-DEBT). `get_client_streak` (migration 095) scans the spine for a harness (`scripts/perf-baseline.ts`) and no product surface.
- **One more relation for the lock to hold.** The view was owner-rights over the health-PII tables until migration 123 pinned `security_invoker` — closed by migration 201's lock, but every view is one more thing `npm run check:rls` clause 3 must hold, and a view that re-joins what its base tables already answer holds nothing.
- **The note has a reader and no writer, and the client app has no note.** `daily_logs.notes` is read by the check-in AI prompt (`utils/ai-prompt-day.ts:124`) and carried as `DailyLog.notes` on the check-in context wire; nothing in the app writes it — the wellness card's schema (`lib/validations/daily-log-cards.ts`) is `.strict()` and refuses a `notes` key, and the only writer was the Daily Pulse's RPC. DEV's 1,978 non-empty notes on 163 clients are seed and smoke residue (the seed writes one on 12% of days; the two September rows are the AI-review smoke's). PROD holds 0 rows in all four tables. The owner's ruling (D1, 2026-09-25): the client app has no day note, so the database keeps none.

The target, from commit 12's bullets as the owner settled it: every client log its own table found by client and date — wellness, nutrition, habits, workouts, measurements — with no parent row; the day note dropped; the spine and its view gone; the per-card client endpoints byte-identical.

## 2. The target shape

**Two tables make a day, each found by `(client_id, date)`: `wellness_logs` and `nutrition_logs`.** Both keep every column they have but `daily_log_id`. No table is created.

```sql
ALTER TABLE public.wellness_logs  ADD CONSTRAINT wellness_logs_client_date_key  UNIQUE (client_id, date);
ALTER TABLE public.nutrition_logs ADD CONSTRAINT nutrition_logs_client_date_key UNIQUE (client_id, date);
```

and, in the same migration, the removals in dependency order — the view before the columns it selects, the functions before the table their bodies name, the spine last:

```sql
DROP VIEW IF EXISTS public.daily_logs_full;
ALTER TABLE public.wellness_logs  DROP COLUMN IF EXISTS daily_log_id;   -- its FK and UNIQUE (daily_log_id) go with it
ALTER TABLE public.nutrition_logs DROP COLUMN IF EXISTS daily_log_id;
DROP INDEX IF EXISTS public.idx_wellness_logs_client_date;              -- the UNIQUE above serves (client_id, date) both ways
DROP INDEX IF EXISTS public.idx_nutrition_logs_client_date;
DROP TABLE IF EXISTS public.training_logs;                               -- D2
DROP FUNCTION IF EXISTS public.upsert_daily_log_atomic(uuid, date, text, jsonb, jsonb, jsonb);
DROP FUNCTION IF EXISTS public.upsert_daily_log_atomic(uuid, date, text, jsonb, jsonb, jsonb, uuid, uuid);
DROP FUNCTION IF EXISTS public.get_client_streak(uuid, date, date);      -- D4
DROP TABLE IF EXISTS public.daily_logs;                                  -- its notes, 4 indexes, trigger and clients FK go with it (D1)
```

**Rules of the shape** (each one exists to delete a rule that exists today):

1. **A day-form row is found by `(client_id, date)` and by nothing else.** The UNIQUE on each table is the upsert's conflict target and every reader's key; there is no parent row and no child id. The plain `(client_id, date DESC)` indexes on the two children are redundant once the UNIQUE exists — a btree serves `ORDER BY date DESC` backwards — and are dropped; `EXPLAIN` on the feed's chunked read and the series read at execution confirms the UNIQUE is chosen (the measurement-log workstream's commit 4 did the same check).
2. **A day is assembled at read, never stored.** `getDailyLogs(clientId, from, to)` and `getTodayLog(clientId, date)` (`services/daily-logs-service.ts`) read the two tables over the range in parallel, plus the computed targets they already read, and fold them per date into the flat `DailyLog`; a date is listed when either table has a row on it. The attention feed's batch reader does the same for its roster (two chunked, paged table reads in place of one view read, both ordered `(date DESC, id)`, merged per client and date in `groupClientData`). The check-in submit's five averages, the check-in context's `dailyLogs`, the review input, the coach's `GET /api/clients/[id]/daily-logs` and the Overview's wellness cards all read through those two functions and change nothing.
3. **The wire is the day, not a row.** Three keys on `DailyLog` are the spine row's own facts and cannot survive it: `id` becomes the date (D3 — the `NutritionEvent.id` precedent: stable and unique per client, the same before and after every write of the day), `createdAt` the earliest `created_at` among the day's rows and `updatedAt` the latest `updated_at`. **Every other key is byte-identical** on every route that carries a day: the two per-card `PATCH` responses, `GET /api/client/daily-logs/[date]/wellness`, `GET …/nutrition` (untouched — it already reads `nutrition_logs` and the computed day), `GET /api/client/check-in-context`'s `dailyLogs`, and the coach's `GET /api/clients/[id]/daily-logs`. Proven with recorded responses before and after (§5).
4. **The three legacy training keys and the note go** (D1, D2): `DailyLog.trained`, `trainingSessionId` and `trainingData` were filled from `training_logs`, which nothing has written since the Daily Pulse retired; `DailyLog.notes` was filled from the spine, which nothing writes and the client app cannot. All four leave the type, the two row mappers, the AI prompt's day note line (`utils/ai-prompt-day.ts:124`) and the RN reference. For any day a client can still write they were already absent.
5. **A logged day's definition does not change.** `loggedDays` and its predicates (`hasWellnessReading`, `hasNutritionEntry`) stay as they are — the feed assembles the five sources from rows it now reads directly, a wellness date from a wellness row and a nutrition date from a nutrition row — and `lib/logged-days-ownership.test.ts` keeps its spine rule as the guard against a parent row returning. That the flat tables make "a row exists" and "carries a reading" the same thing in practice (DEV: zero all-null rows; the cards refuse an empty save) is a simplification for a later change, not this one.
6. **A card write is one statement**: the card's own upsert on `(client_id, date)`. The nutrition stamp (`nutrition_plan_id` from `resolvePlanContextForDate`) and the `readBack` of the whole day for the response are unchanged; `ensureSpine` and the "benign half-written day" go. The day rule (`assertCanEdit`) and both routes' code are untouched.
7. **What is deleted at the end (commit 2):** `daily_logs` and its notes, `daily_logs_full`, the two `daily_log_id` columns with their FKs and UNIQUE indexes, the two plain child indexes, `training_logs`, both `upsert_daily_log_atomic` overloads, `get_client_streak`; in code, `ensureSpine`, `DailyLogFullRow`, the feed's `DailyLogRow`, `calculateStreaks`, `calculateStreakFromLogs` and their tests, the `training_logs` and note legs of the seeds.

**What appears for free, not built here:** a wellness-only point read for `GET …/wellness` (rule 3 keeps it through `getTodayLog` — five scores from two point reads and a target computation is today's cost, and commit 1 may switch it to a sparse `wellness_logs` read, wire identical, if the session prefers; say which in the plan review).
